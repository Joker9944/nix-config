# DP-2 colour and HDR

DP-2 is an LG 27GL850-B, the only HDR-capable panel across both hosts. Its EDID advertises ST.2084 (PQ), BT.2020 RGB/YCC, MaxCLL 400 cd/m², MaxFALL 344 cd/m², min luminance 0.098 cd/m², and native primaries near DCI-P3. Wide gamut, but DisplayHDR-400 class with no local dimming — it accepts an HDR10 signal considerably better than it displays one, which is why HDR here is **on demand rather than always on**: the desktop stays sRGB and only a fullscreen app presenting a PQ surface flips the panel.

Most of that needs no configuration, and the absences are deliberate:

* `CMonitor::supportsHDR()` derives from the EDID (`supportsBT2020` && `hdrMetadata->supportsPQ`), so it is already true for DP-2 with nothing set.
* `render:cm_auto_hdr` defaults to `1` and `render:cm_enabled` to `true` — the fullscreen auto-switch is upstream default behaviour, not restated in nix.
* `min_luminance` / `max_luminance` / `max_avg_luminance` default to `-1`, which reads the EDID figures above. Pinning them in nix would copy panel data into a file that cannot follow a monitor swap.

The one thing configured is `bitdepth = 10` on the DP-2 monitor rule. Hyprland does **not** raise bit depth on its own when wide-gamut or HDR engages — it warns and raises an on-screen notification instead (there is a standing `FIXME` beside that check in `Renderer.cpp`), and HDR at 8 bit bands. It also tips `render:use_fp16`'s `auto` into using the fp16 internal buffer.

Since hyprland is pinned to an upstream tag bumped independently of the nixos release train (see [release-policy](/decisions/release-policy.md)), that "correct by default" set is a live dependency: if HDR stops auto-engaging after a bump, check whether `cm_auto_hdr`'s default moved before suspecting the monitor rule.

`cm` is left at `srgb`. The panel's native gamut is wider than sRGB, so unless its own OSD clamps, desktop colour runs oversaturated; `cm = "edid"` is the lever that would move that correction into hyprland instead.

Games reach HDR through Proton's wayland driver, not gamescope. Per title: launch options `PROTON_ENABLE_WAYLAND=1 PROTON_ENABLE_HDR=1 DXVK_HDR=1` **and** the compatibility tool forced to a GE-Proton build. Valve's builds ship no `winewayland.drv` and ignore both variables silently; Steam's global default tool loses to Valve's per-title mapping, so only the per-game force takes effect. `~/.local/share/Steam/logs/compat_log.txt` says which build actually won.

`quirks:prefer_hdr` is deliberately unset — DXVK negotiates against the color-management protocol's *supported* transfer functions, not the *preferred* image description that `prefer_hdr` overrides (gamescope is the client that reads the latter). It would also hurt here: real EDID luminances reach clients only when `monitors().size() == 1`, so with three monitors it would advertise `DEFAULT_HDR_IMAGE_DESCRIPTION`'s 10000 cd/m² to a 400-nit panel.

Live experiments on any of this go through `hyprctl eval`, not `hyprctl keyword`; see [hyprland-lua-config](/architecture/hyprland-lua-config.md).

# Host record & mixin selection

Host record: `flake.nix#nixosConfigurations`, selecting `profile = "hyprland-desktop"` — the source of the graphical baseline (see [profiles](/architecture/profiles.md)). `modules/nixos/hosts/HAL9000/mixins.nix` holds only the deltas on top: `nvidia`, `steam` (with its `resolution`), `ffmpeg`, `docker`, `windowsSupport`. Per-host quirks (red limine boot branding, `system.stateVersion = "24.05"`, regreet window rule pinned to DP-2): `modules/nixos/hosts/HAL9000/default.nix`.

Home-manager side: `modules/home/users/joker9944/hosts/HAL9000/default.nix`. Host-specific additions worth calling out:

* Gaming stack: Prism Launcher, Lutris, Steam autostart entry.
* Multiple Librewolf profiles: Work / Homework.
* `programs.yas.config.gpu = true;` — HAL9000-only because the GPU widget depends on the discrete GPU.
* GNOME touchpad disabled — guarded by `mixins.desktopEnvironment.gnome.enable`, so it's inert under hyprland.
