# Update Log

## 2026-08-10

* **Feature**: HDR on DP-2 (HAL9000), on demand rather than always on. The nix change is a single `bitdepth = 10` on the DP-2 monitor rule — everything else HDR needs was already upstream default: `supportsHDR()` derives from the EDID (`supportsBT2020` && `hdrMetadata->supportsPQ`, both true for this panel), `render:cm_auto_hdr` defaults to `1`, `render:cm_enabled` to `true`. Bit depth is the one thing hyprland won't raise for itself when wide-gamut/HDR engages: it warns and shows an on-screen notification instead (standing `FIXME` beside the check in `Renderer.cpp`), and HDR at 8 bit bands. **Design call — always-on HDR rejected on hardware grounds**, not preference: the LG 27GL850-B's EDID reports MaxCLL 400 / MaxFALL 344 / min 0.098 cd/m² with no local dimming, so a permanent PQ desktop trades real black level and SDR brightness for a signal the panel can't exploit. On-demand costs nothing when idle since the fullscreen auto-switch reverts to `m_cmType` on exit. **Deliberate absences**: `cm_auto_hdr` left unset (it is the upstream default; restating it would be noise, at the price of a live dependency on a default-branch pin — recorded in the host doc rather than pinned in nix), and `min_luminance`/`max_luminance`/`max_avg_luminance` left at `-1` so they read the EDID instead of freezing panel data into a file that can't follow a monitor swap. Gamescope untouched: games take the Proton wayland-driver route (`PROTON_ENABLE_WAYLAND=1 DXVK_HDR=1`, per-title launch options — XWayland cannot declare an HDR surface, and a global env var would force the still-rough wayland driver onto every Proton title). `cm` stays `srgb`; the panel is wider than sRGB so desktop colour is likely oversaturated, but whether hyprland or the monitor's OSD should own that correction is untested and left open.
* **Note**: `quirks:prefer_hdr` was investigated and **not** landed — DXVK negotiates against the colour-management protocol's supported transfer functions, not the preferred image description that `prefer_hdr` overrides, so `bitdepth = 10` stayed the entire nix change. The blocker was on the Steam side: a per-title Valve mapping outranks the global default compat tool, and Valve's Proton builds ship no `winewayland.drv`, so the launch-option env vars were read by nothing. Both recorded in [hosts/HAL9000](/hosts/HAL9000.md).
* **Creation**: Added the *Runtime control is `eval`, not `keyword`* section to [architecture/hyprland-lua-config](/architecture/hyprland-lua-config.md). `hyprctl keyword` is **unregistered** under the lua config manager and returns `unknown request`; `eval`/`repl` evaluate lua against the live config and `dispatch` is a wrapper for `hl.dispatch(…)`. A trap worth recording because the verb doesn't exist at all — every wiki example reaches for it. It also completes the runtime-validation section above it: since a wrong rule key builds clean and fails silently, `eval` is the short loop for finding out whether hyprland accepts a key.
* **Feature**: The YouTube PWA window is now exempt from the global `decoration.active_opacity` / `inactive_opacity` (0.95 / 0.9) — a `window_rule` with `opaque = true` in `users/mixins/pwas/youtube/default.nix`, reusing the `siteId` already bound there. **Design call**: the rule lives in the DE-agnostic `pwas` category rather than the hyprland tree, accepting a `pwas` → hyprland coupling in exchange for keeping everything about the YouTube PWA in one file and not duplicating the ULID. The alternative considered was a `hyprland/pwas.nix` matching `FFPWA-.*` for all PWAs; rejected as a scope widening. The assignment is inert (not an eval error) when hyprland is disabled. Matches on `initial_class`, not `class`: `m_initialClass` is captured once at map, `m_class` is re-fetched on every `metadataChanged`, so a client-driven `set_app_id` can't silently drop the rule.
* **Creation**: New concept [architecture/hyprland-lua-config](/architecture/hyprland-lua-config.md) — the bundle had no hyprland concept despite the repo's large hyprland tree and its `configType = "lua"`. Scoped to what doesn't rot: where `settings` nests (config vars under `settings.config`, rules/binds at top level), that `window_rule` merges across the tree, that global translucency originates in the `style.opacity` mixin, and the load-bearing fact that rule keys are validated at **runtime** — home-manager passes the attrset through verbatim, so a misspelled key builds clean, activates clean, and silently does nothing, surfacing only in `hyprctl configerrors`. Hence the verify loop (`configerrors` + `getprop`; there is no `hyprctl rules`). **Deliberately not captured**: any enumeration of match properties, effect names, or their value types. `flake.nix` pins hyprland to the *default branch*, which advanced through ~20 revisions in the three weeks to 2026-08-09, so such a table is stale within days — the same reasoning [lookup-hm-option](/workflows/lookup-hm-option.md) uses to keep the hm trap table in the skill rather than the bundle. The concept carries a `nix flake archive`-based grep recipe against the pinned tree instead, keyed on the identifiers `MATCH_PROP_STRINGS` / `EFFECT_STRINGS` / `WINDOW_RULE_EFFECT_DESCS` rather than on file paths, so it survives upstream reshuffling and fails visibly (empty grep) rather than silently when it doesn't.
* **Rejected**: A hyprland MCP server, and a pinned `hypr-rules` tool mirroring `mkOptionsTool`. The MCP fails on the same ground `CLAUDE.md` already prefers `hm-options` over the `nix` MCP — it would serve live upstream, not this flake's pin, and with a daily-moving pin those diverge constantly; there is also no hyprland analogue of search.nixos.org to query, so it would reduce to scraping the wiki. The pinned tool is technically sound (the data is in the store, extractable at build time) but does not amortize: `git log -S"window_rule" -- users/mixins/` shows **2 commits in 12 months**, versus `programs.*` lookups on nearly every module edit. Revisit if window-rule authoring becomes routine.
