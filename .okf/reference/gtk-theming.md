# Why the theme is mandatory

The stock stylesheets are compiled flat. GTK3's built-in Adwaita declares 36 `@define-color` names
and references them **zero** times; GTK4's built-in `Default` does the same. Sass resolved every
`darken()` / `mix()` at build time, so those names survive only as an API for third-party app CSS —
the stylesheet itself never reads them. Overriding them from `extraCss` changes nothing.

adw-gtk3 is generated from libadwaita's stylesheet, which keeps `mix()` / `alpha()` as *runtime* CSS
functions over the named colours — its GTK3 sheet references `@window_bg_color` 228× and
`@accent_bg_color` 176×. That propagation is the only reason the generated CSS
has anything to bind to, so the dependency cannot be dropped for a pure-`extraCss` approach.

# Who needs it

| Consumer | Toolkit | Needs adw-gtk3 |
|---|---|---|
| `inkscape`, `meld`, `librewolf` | GTK3 | yes — nothing else is overridable |
| `regreet` | GTK4, **no libadwaita** in its `buildInputs` | yes — otherwise fully unthemed |
| Electron / Chromium | GTK4, no libadwaita | yes |
| `yas`, GNOME apps, portals | GTK4 + libadwaita | no — libadwaita bridges `@define-color` → `--var` itself |

libadwaita apps ignore `gtk-theme-name` by design, and the theme agrees: `libadwaita-tweaks.css`
opens with *"These fixes are not for libadwaita apps."*

# Applying it to GTK4

`gtk.gtk4.theme` does not put the theme on GTK4's search path. It triggers a home-manager workaround
that `@import`s the theme into `~/.config/gtk-4.0/gtk.css` — the *user* stylesheet, the one channel
libadwaita apps cannot opt out of. Name the theme directly instead:

```nix
gtk4 = {
  theme = null;
  extraConfig.gtk-theme-name = themeName;
};
```

`theme = null` on its own is a trap: `mkGtkSettings` emits `gtk-theme-name` only when `theme != null`,
so dropping it without `extraConfig` un-themes every non-libadwaita GTK4 app. The package still
reaches the profile — and thus `XDG_DATA_DIRS` — through `gtk.theme` for GTK 2/3.

# What to override

Override every upstream default that is an **opaque literal** — it cannot blend with the palette.
Leave every **translucent** one (`rgba`, or `color-mix` over `currentColor`): those composite
correctly on any background, and upstream branches their alpha per variant. Upstream's own defaults
are the authority: libadwaita's `src/stylesheet/_colors.scss` and
adw-gtk3's `src/sass/_defaults.scss`.

Re-bridging named colours to their `--var` counterparts is dead weight — libadwaita does it in its
own `:root`, and adw-gtk3's `gtk-4.0` sheet ships the same block, so regreet gets it too. Three
exceptions survive in `_defaults.scss`: the nine `--accent-<name>` entries and
`--accent-bg-color` / `--accent-fg-color`, re-pinned because `libadwaita-tweaks.css` hardcodes the
accent to blue, and `--overview-*`, which upstream sets only as a custom property with no
named-colour counterpart.

# How the CSS is generated

`libSchemes.mkGtkThemeCss { scheme, accents, accent }` compiles `lib/init/mkGtkThemeCss/scss/` with
dart-sass into a directory holding `gtk3.css` and `gtk4.css`. Consumers `@import` those store paths
from `extraCss`, so evaluation never reads the derivation — no IFD. Entry points are static, one per
toolkit and variant. Colour maths stays in `libSchemes` where `tests/lib/` can reach it.

Two kinds of value, which do not mix:

* **Literals** — `settings/_palette.scss`, generated by Nix from the scheme. `_defaults.scss` reads
  only these: a reference form is invalid inside `@define-color` and self-referential inside `:root`.
* **References** — `settings/_colors.scss`, `@name` on GTK3 and `var(--name)` on GTK4. For widget
  declarations only, so rules track the colour rather than freezing it. A misspelled one is a build
  error instead of a declaration GTK silently drops.

## Load paths are not a merged tree

`abstracts/` (from the `adw-colors` input) and the generated palette are separate `SASS_PATH` roots.
Sass tries a relative import against the importing file's real location, then joins the literal path
onto each root — so `../` walks *out* of a root, never up a virtual tree. Cross-root imports are
spelled from the root; `settings/` is the only directory that needs to.

## sass and GTK collide

Two GTK constructs cannot be written literally in SCSS, which is why adw-colors' `gtkcolor` and
`gtkalpha` are used rather than reimplemented — they are mandatory, not sugar:

* A bare `@name` in a value position is a **parse error**; `@` starts an at-rule. It has to be built
  as a string.
* sass has its own `alpha()` taking one argument, where GTK's takes two — `alpha(currentColor, 0.5)`
  fails to compile.

`currentColor` is the only value that must stay a runtime CSS function; everything else is
precomputed, so GTK's `mix()` never appears and cannot collide with sass's.
